# Release Workflow

Automates the release process for the release-toolkit gem.

## Prerequisites

- You must be on the `trunk` branch
- Working directory should be clean. Unchecked files are fine, but no changes to tracked files.
- You need push access to the repository

## Workflow Steps

### Step 1: Run the release preparation rake task

Run:

```bash
echo "" | bundle exec rake new_release
```

The `echo ""` accepts the default version. This task is **interactive** - it will:

1. Show the current version and pending CHANGELOG entries
2. Suggest a version number based on SemVer rules
3. Accept the default or (if piping a specific version) use that

The task will then:

- Create a `release/<version>` branch
- Update `version.rb` with the new version
- Update `CHANGELOG.md` (move Trunk entries to the new version section)
- Commit and push the changes
- Open a browser with the PR creation URL (ignored when running non-interactively)

**Note the version number** from the output - you'll need it for subsequent steps.

> **TODO:** The rake task currently always opens a browser. Consider adding an option to skip this when running from an agent/CI context.

### Step 1b: Amend the commit with proper authorship

The release commit should be authored by Claude with the user as co-author. After the rake task completes, amend the commit:

First, get the user's git identity:

```bash
git config user.name
git config user.email
```

Then amend the commit with Claude as author and user as co-author:

```bash
git commit --amend --no-edit \
  --author="Claude <noreply@anthropic.com>" \
  --trailer "Co-Authored-By: <USER_NAME> <<USER_EMAIL>>"
git push --force-with-lease
```

### Step 2: Create the Pull Request

After the rake task pushes the branch, create the PR using `gh`:

```bash
/opt/homebrew/bin/gh pr create \
  --base trunk \
  --title "Release <VERSION> into trunk" \
  --body "$(cat <<'EOF'
Releasing new version <VERSION>.

## What's Next

Once merged, a GitHub Release will be created which will trigger the CI job to push the gem to RubyGems.

---

Generated with the help of [Claude Code](https://claude.ai/code)
EOF
)"
```

Replace `<VERSION>` with the actual version number.

### Step 3: Add labels and reviewers

```bash
/opt/homebrew/bin/gh pr edit --add-label "Releases"
```

The README might suggest to add @wordpress-mobile/apps-infrastructure as a reviewer, but we now longer use that group and prefer individual pings.
The user will handle adding the appropriate reviewers.

### Step 4: Inform the user and wait for merge

Tell the user:

> PR created and configured. The PR needs to be reviewed and merged by the team.
> I'll check periodically for the merge status. You can also tell me when it's merged.

Run a background polling loop that checks every 60 seconds:

```bash
PR_NUMBER=<PR_NUMBER>
while true; do
  STATE=$(/opt/homebrew/bin/gh pr view $PR_NUMBER --json state -q '.state')
  echo "$(date '+%H:%M:%S') - PR #$PR_NUMBER state: $STATE"
  if [ "$STATE" = "MERGED" ]; then
    echo "PR merged!"
    break
  fi
  sleep 60
done
```

Run this in the background and check its output periodically. When the state is `MERGED`, proceed to Step 5.

If the user indicates the PR was merged, verify with a single check then proceed.

### Step 5: Create a DRAFT GitHub Release

Once the PR is merged, extract the changelog content for this version and create a **draft** GitHub release.

**IMPORTANT:** Always create the release as a draft. We do not want unsupervised releases - the user must review and manually publish.

First, get the changelog content for the released version from `CHANGELOG.md`. The format is:

```markdown
## <VERSION>

### Breaking Changes
...
### New Features
...
### Bug Fixes
...
### Internal Changes
...
```

Extract everything between `## <VERSION>` and the next `## ` header.

Then create the **draft** release (note the `--draft` flag). Include the "Generated by Claude" footer:

```bash
/opt/homebrew/bin/gh release create "<VERSION>" \
  --target trunk \
  --title "<VERSION>" \
  --draft \
  --notes "$(cat <<'EOF'
<CHANGELOG_CONTENT>

---

Generated with the help of [Claude Code](https://claude.ai/code)
EOF
)"
```

### Step 6: Prompt user to review and publish

Inform the user:

> Draft release `<VERSION>` created and ready for review.
>
> - PR: <PR_URL>
> - Draft Release: <RELEASE_URL>
>
> **Action required:** Please review the draft release and publish it when ready.
> Publishing the release will create the git tag and trigger the CI workflow to push the gem to RubyGems.

## Error Handling

- If `rake new_release` fails, show the error and stop
- If PR creation fails (e.g., branch doesn't exist), check if the rake task completed successfully
- If the PR can't be found after creation, list recent PRs to help identify it
- If release creation fails, provide the changelog content so the user can create it manually

## Manual Fallback

If any automated step fails, provide clear instructions for the user to complete manually:

1. Create PR at: `https://github.com/wordpress-mobile/release-toolkit/compare/trunk...release/<VERSION>`
2. Add `Releases` label
3. Add appropriate reviewers
4. After merge, create a **draft** release at: `https://github.com/wordpress-mobile/release-toolkit/releases/new` (select "Save draft", not "Publish release")
5. Review the draft and publish when ready
